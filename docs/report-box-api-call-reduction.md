| 作成日 | 2026-11-05 |
| 関連資料 | [SS 画面 技術仕様書](./spec-ss-screen.md) / [useBoxExplorer フック 仕様書](./spec-use-box-explorer.md) |

## 1. 要約

- 自社の Box 契約では、API 呼び出しが **月間 100,000 回** までに制限されている。想定利用者は約 400 人。
- 現行の SS 画面は、**1 人が 1 時間操作するだけで約 100 回** の API 呼び出しを消費している（担当者の観測値）。このまま全社展開すると、月間の上限を超える見込みだった。
- 原因を調べた結果、不要な呼び出しではなく、**画面の作りに起因する「正当だが過剰な呼び出し」** が主因だった。特に、フォルダを 1 つ移動するたびに、コラボレーター一覧を自動で取得していた点が大きい。
- 対策として、次の 4 点を実施した。
  1. コラボレーター一覧を「畳んだ状態」を初期値とし、開いたときだけ取得する。取得結果は 5 分間キャッシュする（**暫定的に、キャッシュは既定で無効**。`VITE_BOX_COLLABORATIONS_CACHE=true` で復活できる）。
  2. 画面へ戻るときの復元で、不要なルートフォルダの取得をやめる。
  3. 画面を離れるときに Box のエクスプローラーを破棄する。
  4. ファイル・フォルダの変更系操作（アップロード等）を画面上で無効にする。
- さらに、Explorer のフォルダ取得（設定では削減できない）を、短時間キャッシュする **試作** を実装した（第 4.5 節）。効果は、同じフォルダの再訪の割合で決まり、これも未測定である。開発時に、命中・未命中を計測できるようにしてある。
- **削減効果は、現時点では実測していない。** 本書では、呼び出しの構造から導いた見積りを示し、実測の手順を第 7 節に記す。

## 2. 背景と課題

### 2.1 制約

| 項目 | 値 | 出所 |
| --- | --- | --- |
| 月間 API 呼び出し上限 | 100,000 回 | 自社プランの契約内容 |
| 想定利用者数 | 約 400 人 | 担当者提供 |
| 1 人あたりの月間の目安 | 約 250 回（100,000 ÷ 400） | 上記から算出 |
| 現状の消費 | 1 人が 1 時間触ると約 100 回 | 担当者の観測 |

月間 250 回は、現状の消費で換算すると **1 人あたり月 2.5 時間分** にすぎない。利用者の一部が長く使うだけで、上限を超える。

### 2.2 呼び出しの発生源

SS 画面で Box の API を呼ぶ処理は、次の 2 系統に分かれる。

| 系統 | 呼び出し元 | 主なエンドポイント |
| --- | --- | --- |
| A. エクスプローラーの表示 | Box UI Elements の Content Explorer（ブラウザへ埋め込み） | フォルダ取得（フォルダ情報とその直下の一覧） |
| B. コラボレーション設定 | 本アプリ（`ssSlice` の thunk） | フォルダのコラボレーター一覧取得、追加、更新、削除 |

## 3. 原因分析

対策前（コミット `96428bc` 時点）のソースを調査した。

### 3.1 コラボレーター一覧が、フォルダ移動のたびに自動取得されていた

- フォルダが変わるたびに、一覧の取得が必ず実行されていた。キャッシュはなく、同じフォルダへ戻っても取得し直していた。
- その結果、**フォルダ 1 回の移動につき、系統 A の 1 回と系統 B の 1 回の、計 2 回以上を消費** していた。
- 利用者の多くは、目的のフォルダを探して通り過ぎるだけで、一覧は最終的な 1 フォルダでしか使わない。通過したフォルダ分の取得は、実質的に無駄になっていた。

### 3.2 復元時に、使われないルートフォルダを取得していた

- SS 画面から他の画面へ移動し、再び戻ると、離脱時のフォルダを復元する。
- 従来は、「ルートを表示してから、離脱時のフォルダへ移動する」という 2 段階で復元していた。ルートの取得は、結果が使われずに捨てられていた。

### 3.3 エクスプローラーの取得は、設定で削減できない

Box UI Elements v23.0.0（本アプリが読み込んでいるバージョン）のソースを確認した。

- フォルダの取得（`fetchFolder`）は、`forceFetch: true` を固定で渡している（[`ContentExplorer.tsx`](https://github.com/box/box-ui-elements/blob/v23.0.0/src/elements/content-explorer/ContentExplorer.tsx) の 588 行付近）。
- そのため、**訪問済みのフォルダへ戻る場合でも、毎回 API を呼ぶ**。エクスプローラーのインスタンスを使い回しても、削減にはならない。
- したがって、フォルダ移動 1 回につき 1 回の呼び出しは、現状の方式では **削減できない下限** である。

### 3.4 画面を離れてもエクスプローラーが破棄されていなかった

- 画面を離れるときに、エクスプローラーを破棄する処理（`hide()`）がどこからも呼ばれていなかった。
- Box 側の画面部品（API 接続とキャッシュを含む）が、メモリ上に残り続ける。**API 呼び出し回数を増やす原因ではない** が、不具合の温床になる。

### 3.5 変更系の操作が、画面上で有効になっていた

- エクスプローラーの既定では、アップロード、削除、名前変更、フォルダ作成が有効（同ソースの既定値）。
- 本アプリのエクスプローラーは、コラボレーション設定の対象フォルダを選ぶ目的で使う。ファイルの変更は運用上想定しておらず、操作されると呼び出しが増えるうえ、一覧が変化して不整合の原因にもなる。

## 4. 対策の内容

### 4.1 コラボレーター一覧を、開いたときだけ取得する

| 項目 | 変更前 | 変更後 |
| --- | --- | --- |
| 初期状態 | 常に表示し、自動取得 | 畳んだ状態。取得しない |
| 取得のタイミング | フォルダが変わるたび | 一覧を開いたとき |
| フォルダ移動時 | 新しいフォルダの一覧を取得 | 畳んだ状態に戻る（取得しない） |
| 同じフォルダを再び開く | 毎回取得 | 5 分以内なら取得しない |

- 一覧の見出しを、開閉ボタンにした（アクセシビリティ属性 `aria-expanded` を付与）。
- キャッシュはフォルダごとに取得時刻を持ち、**5 分（300,000 ミリ秒）** を超えると取得し直す。

#### キャッシュの無効化

コラボレーターの追加・削除・ロール変更を行ったときは、**全フォルダ分のキャッシュを破棄** する。

- 理由: 一覧には親フォルダから継承された設定も含まれるため、あるフォルダへの変更は、配下のフォルダの一覧にも影響する。
- 一覧が開いている場合は、その場で最新の一覧を取得し直す。畳んでいる場合は、次に開いたときに取得する。

#### 追加時の重複チェックは、常に最新を取得する

- 追加の前に、同じコラボレーターが設定済みでないかを確認している。
- キャッシュが有効な状態でも、**この確認のときだけは必ず Box から最新を取得する**。他の人が 5 分以内に同じ対象を追加していた場合に、古いキャッシュで確認をすり抜けるのを避けるため。
- 追加操作は人手で行うため回数が少なく、1 回の追加につき 1 回の取得が増えるコストは小さい。
- なお、この確認はあくまで事前確認である。確認から追加までの間に他の人が追加する可能性は残り、最終的な防止は Box 側の拒否に依存する（第 6 節）。

### 4.2 復元時に、ルートを経由しない

- 離脱時のフォルダがルートと異なる場合、エクスプローラーを最初から **そのフォルダで表示** する（`show()` のオプション `currentFolderId` を指定）。ルートの取得を省く。
- パンくずの起点となるルートの指定は、従来どおり維持する。パンくずは、取得したフォルダの階層（`path_collection`）を、ルートから先で切り出して表示される（`Breadcrumbs.tsx` の `filterCrumbs`）。そのため、ルートからの階層で表示される。
- 戻る・進む（フォルダの履歴）は、Redux 上の履歴を使うので、この変更の影響を受けない。
- 留意点: `currentFolderId` は Box の公式ドキュメントに記載がない。v23.0.0 のソース上、`show()` に渡したオプションがそのまま画面部品の入力として渡されることを根拠にしている。バージョンを上げる場合は、この挙動が維持されているかの確認が必要。

### 4.3 画面を離れるときに、エクスプローラーを破棄する

- 画面を離れる（アンマウントする）ときに `hide()` を呼び、Box 側の画面部品を破棄する。
- 表示前に `hide()` を呼ぶと例外になるため、表示済みかを判定してから呼ぶ。破棄に失敗しても、画面遷移は妨げない。

### 4.4 変更系の操作を無効にする

- エクスプローラーに `canUpload: false`、`canDelete: false`、`canRename: false`、`canCreateNewFolder: false` を指定した。
- **この設定は、画面上のボタンを表示しないだけである。** Box 側の権限は変わらない。Box の Web 画面などから変更されることは防げない。

### 4.5 フォルダ取得のキャッシュ（試作）

> 設計・仕様・運用の詳細は、[Box フォルダ取得キャッシュ 設計・仕様書](./spec-box-folder-cache.md)を参照する。

Explorer のフォルダ取得は、設定では減らせない（3.3 節）。そこで、Explorer の `show()` に渡せる通信の中継処理（`requestInterceptor` / `responseInterceptor`）を使い、**同じ要求の応答を 5 分間保存し、通信せずに返す** 試作を実装した（`src/lib/boxFolderCache.ts`）。

| 項目 | 内容 |
| --- | --- |
| 対象 | フォルダ取得（`GET /folders/{id}`）のみ。`/items`、`/collaborations` 等は対象外 |
| 保存 | 成功（200）の応答を、要求のパラメータ（並び替え、ページ位置など）ごとに保存する |
| 返却 | 有効時間（5 分）内の同じ要求は、axios の通信部分（`adapter`）を差し替えて、通信せずに保存済みの応答を返す |
| 有効時間の延長 | キャッシュから返した応答には印を付け、再保存しない（有効時間が延びない） |
| 安全策 | 保存・返却のときに深いコピーを使う（Box のコードが応答を書き換えても、保存済みの内容を壊さない）。件数の上限（200）。期限切れの掃除 |
| ユーザーの分離 | キーにアクセストークンを含める。ユーザーやトークンが変わると、別のキーになる。ログには、トークンを含まない形で出力する |
| 無効化 | 環境変数 `VITE_BOX_FOLDER_CACHE=false` で無効にできる（既定は有効） |
| 計測 | 開発時は、命中・未命中の件数をコンソールに出す。実際の利用で、再訪の割合を直接測れる |

- **効果は、同じフォルダを再び開く割合で決まる。** 初めて開くフォルダは必ず通信する。「戻る」ボタンの利用や、領域の行き来が多いほど効く。一方向に辿るだけの利用では、ほとんど効かない。
- 保存の仕組みは、Jest 上の実際の axios で、2 回目の要求が通信まで届かないことを確認した（自動テスト）。
- **未検証**: Box の画面部品（Box が内部に持つ axios）で、想定どおり動作するか。開発環境で、ネットワークタブを見て確認する必要がある（第 7 節）。
- 画面から変更系の操作を無効にしているため（4.4 節）、このアプリ内の操作で応答が古くなることはない。他の人の変更は、最大 5 分は反映されない。
- **利用者が古い情報を解消できるよう、パスバーに「更新」ボタンを 1 つ置いた。** 押すと、フォルダ取得のキャッシュと、コラボレーター一覧のキャッシュを全て破棄し、現在のフォルダを取り直す（通信は、一覧が畳まれていれば 1 回、開いていれば 2 回）。フォルダの表示とコラボレーター一覧を、まとめて最新にする。

## 5. 期待される効果（見積り）

> **注意: 以下は、呼び出しの構造から導いた見積りであり、実測値ではない。**

### 5.1 計算式

- 変更前: 消費 ≒ フォルダ移動の回数 × 2（エクスプローラー + コラボレーター一覧）
- 変更後: 消費 ≒ フォルダ移動の回数 + 一覧を開いた回数（+ 追加時の確認）

### 5.2 例

「目的のフォルダを探して 10 個のフォルダを辿り、最後の 1 つでコラボレーター一覧を確認する」場合。

| | エクスプローラー | コラボレーター一覧 | 合計 |
| --- | --- | --- | --- |
| 変更前 | 10 | 10 | 20 |
| 変更後 | 10 | 1 | 11 |

- この例では、約 45 % の削減になる。
- 閲覧が中心で、一覧をほとんど開かない利用者ほど、削減率は 50 % に近づく。
- 一覧を毎回開く利用者では、削減は小さくなる（ただし 5 分以内の再訪はキャッシュが効く）。
- 画面へ戻ったときの復元でも、1 回の削減になる（ルート取得の省略）。

### 5.3 この対策で到達できる範囲

- エクスプローラーの取得（フォルダ移動 1 回につき 1 回）は、設定では **削減できない下限** である（3.3 節）。4.5 節の試作は、この下限を、再訪の分だけ下げる。
- 4.1〜4.4 節の対策だけでは、月間の消費を **およそ半分** にする水準が上限と考えられる。4.5 節の効果は、再訪の割合の測定後に見積もる。現状の消費が上限に対して何倍かによって、十分かどうかが決まる。
- 先月の実際の使用量が分かれば、必要な削減率を確定できる（第 7 節）。

## 6. リスクと留意点

| 項目 | 内容 | 対処・方針 |
| --- | --- | --- |
| 古い一覧の表示 | 他の人が Box 側で変更しても、最大 5 分は古い一覧が表示される。この画面からの変更は即座に反映される | 運用上許容できるかを確認する。許容できない場合は有効時間を短くする |
| 重複追加の最終防止 | 事前確認は最新を取得して行うが、確認から追加までの数秒の間の他者の追加は防げない | Box 側が重複を拒否する場合、既存の失敗メッセージが表示される。実 API が返すエラー形式の確認が必要 |
| 一覧を開く操作の増加 | フォルダを移動するたびに、一覧は畳んだ状態に戻る。続けて確認したい利用者は、毎回開く必要がある | 操作性への影響を利用者に確認する |
| フォルダ取得のキャッシュ | 他の人が Box 側で行った変更（ファイルの追加など）が、最大 5 分は Explorer に反映されない。Box の画面部品が、キャッシュ応答を想定どおり扱うかは、実機で未確認 | 環境変数で無効にできる。開発環境で、ネットワークタブにより確認する |
| `currentFolderId` の依存 | 公式ドキュメントにない挙動に依存している | Box UI Elements のバージョンを固定している（`23.0.0`）。更新時に再確認する |
| 復元先が取得できない場合 | 復元先のフォルダが削除された、または権限がなくなった場合、読み込み中の表示が続く可能性がある | 従来から同様の可能性があった。必要ならルートへ戻す処理を追加する |
| 変更系操作の無効化 | 画面上のボタンを隠すだけで、権限は変わらない | 変更を禁止する必要がある場合は、Box 側の権限で制御する |

## 7. 効果の検証方法（実施予定）

1. **現状の使用量の確認**: Box 管理コンソールの API 使用状況レポートで、直近 1 か月の呼び出し回数と、エンドポイント別の内訳を確認する。「1 人 1 時間で約 100 回」が実測で裏づけられるかも確認する。
2. **上限の数え方の確認**: Box に、Box UI Elements（埋め込みエクスプローラー）の呼び出しが上限に含まれるかを問い合わせる。
3. **変更前後の比較**: ブラウザの開発者ツール（ネットワークタブ）で、同じ操作手順（例: 10 フォルダを辿り、一覧を 1 回確認し、他の画面へ移動して戻る）を、変更前と変更後で実行し、Box への通信回数を比較する。
4. **フォルダ取得のキャッシュの計測**: 開発環境（`npm run dev`）で、ブラウザのコンソールに出る `[boxFolderCache]` のログ（命中・未命中の累計）を確認する。同じ操作を、キャッシュを有効・無効（`VITE_BOX_FOLDER_CACHE=false`）にして比較し、ネットワークタブの `folders` の通信回数が減ることを確認する。
5. **展開後の監視**: 展開後 1〜2 週間の使用量を、手順 1 の方法で確認し、月間上限に対する見通しを再計算する。

## 8. 今回採用しなかった案（参考）

| 案 | 採用しなかった理由 |
| --- | --- |
| エクスプローラーのインスタンスの使い回し | 取得が毎回強制されるため（3.3 節）、削減にならない |
| 閲覧の主導線を Box 本体（Web）へ逃がす | コラボレーションの設定には `can_view_path` の付与が必要で API が必須。また、アプリ内でフォルダを辿る体験が失われる |
| 通信の中継処理（インターセプター）による自前キャッシュ | **試作として実装した**（4.5 節）。効果は再訪の割合次第で、未測定。実機での確認が必要 |
| 契約の上限の引き上げ | 本書の対象外。上記の検証結果によっては、並行して検討する |

## 10. 用語

| 用語 | 意味 |
| --- | --- |
| Content Explorer | Box が提供する、Web ページに埋め込めるファイルブラウザ（Box UI Elements の一部） |
| コラボレーション | Box のフォルダに対する、ユーザーまたはグループへのアクセス権の付与 |
| `can_view_path` | 招待先のフォルダまでの親フォルダの階層を、招待された側が辿れるようにする Box のオプション。本アプリのコラボレーションは常にこれを有効にして作成する |
| 継承 | 親フォルダへのコラボレーションが、配下のフォルダにも及ぶこと |
