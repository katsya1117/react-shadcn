# Box アクセストークンのダウンスコープ設計

SS 画面の Contents Explorer で、名前変更・削除・新規フォルダ作成を使えるようにするための、トークン設計。
**プレビューとダウンロードは、発注元の要望により許可しない**（API 呼び出しの節約。§3 参照）。
あわせて、ファイルへのコラボレーションと、Explorer での選択の扱いをまとめる。

**状態**: 設計案。未実装。API は今モック（`src/api/index.ts` の `getContentsPickerToken`）のため、本物のサーバー側は別途必要。

## 1. 背景と目的

- 現状の Explorer は、変更系の操作をすべて隠している（[SS.tsx](../src/pages/SS.tsx) の `canDelete` / `canRename` / `canCreateNewFolder` / `canUpload` / `canPreview` を `false`。`canDownload` は未指定で、Explorer の既定（有効）のままになっている可能性があり、`false` を明示する）。
- 画面上のボタンを隠すだけで、トークンの権限は変わらない（[spec-ss-screen.md](spec-ss-screen.md) の「既知の制約」参照）。
- 操作を許可するなら、画面の `can*` だけでなく、**トークン側でも許可する操作に絞る**（ダウンスコープ）。多層で守る。

## 2. ダウンスコープの基本

- Box の Token Exchange（RFC 8693）で、元のトークンから、**スコープと対象リソースを絞った短命のトークン**を作る。
- **サーバー側でのみ実行できる**（クライアントシークレット、または JWT が必要）。ブラウザから実行してはならない。
- ダウンスコープは、権限を**絞るだけ**。ユーザー本人の Box 権限を超える操作はできない。
- 有効期限は約 60 分。更新（再発行）の仕組みが要る。
- `resource` に、フォルダまたはファイルの URL を指定すると、そのアイテムと配下だけに使えるトークンになる。

## 3. 機能とスコープの対応

| 機能 | 必要なスコープ | Explorer の prop |
|---|---|---|
| 一覧表示・移動 | `base_explorer` | （常時） |
| 名前変更 | `item_rename` | `canRename` |
| 削除 | `item_delete` | `canDelete` |
| 新規フォルダ作成 | `item_upload` | `canCreateNewFolder` |
| コラボレーションの管理（独自 UI） | 要確認（`item_share` の可能性） | — |

**許可しない操作**: プレビュー（`item_preview` / `base_preview`）とダウンロード（`item_download`）は、トークンに付けず、`canPreview: false` / `canDownload: false` にする。理由は、API 呼び出し回数の節約。1 操作あたりの呼び出し回数は未測定のため、測定したらここに記す。

注意:

- 新規フォルダ作成に要るのは `item_upload`。upload のボタンは `canUpload: false` で隠せるが、トークンの権限としては upload も許可される。
- 上のスコープ名は Box の公式ドキュメントに基づくが、**実装時に、使う Box アプリの設定（アプリのスコープ）と合わせて検証すること**。
- コラボレーション管理に使うトークンが、Explorer と同じものか別かは、現状の仕様書に記載がない。実装前に確認する。

## 4. 発行の設計案

### 4.1 サーバー API（案）

```
POST /api/box/token
{ "rootFolderId": "123456", "scopes": ["base_explorer", "item_rename", ...] }
→ { "accessToken": "...", "expiresIn": 3600 }
```

- クライアントは**スコープの名前ではなく、機能の名前**（例: `rename`）を送るのが望ましい。スコープへの変換はサーバーで行い、クライアントが任意のスコープを要求できないようにする。
- サーバーは、`rootFolderId` が `SHARE_AREAS`（[shareAreaConfig.ts](../src/config/shareAreaConfig.ts)）に含まれるかを検証する。
- `resource` は `https://api.box.com/2.0/folders/{rootFolderId}` にする。トークンが SS の許可ルートの外に使えなくなる。

### 4.2 クライアント側の変更（案）

- トークンを**ルートフォルダ単位**で保持する（今は `user.box.token` に 1 つ）。
- 有効期限（`tokenDt` ＋ 約 60 分）の手前で再発行する。
- 開発用トークン（`localStorage` の `box_dev_token`）は、ダウンスコープされない。本番では使わない。
- `show()` に渡す `can*` は、**トークンに付けたスコープと一致**させる。付けていないスコープの操作を画面に出さない。

### 4.3 ロール出し分け（要判断）

| 案 | 内容 |
|---|---|
| A. 全員に変更系を許可 | 実装は単純。最終的な可否は Box の権限が決める |
| B. ロールで出し分け | 変更系スコープを付けるユーザーを絞る。事故を防げるが、サーバー側の判定が要る |

決定後、この表を更新する。

## 5. 変更系を有効にしたときの影響（アプリ側）

| 対象 | 問題 | 対応の方向性 |
|---|---|---|
| フォルダ取得キャッシュ（`boxFolderCache`、5 分） | 変更しても、一覧が最大 5 分古いまま | `rename` / `delete` / `create` イベントで全破棄する。または変更系リクエストを `requestInterceptor` で検知して破棄する |
| 名前変更 | `ss` スライスの履歴、`currentFolder`、パスバーに古い名前が残る | 現在地・祖先が対象のときは、パスを再構築する |
| 削除 | 現在地・履歴のフォルダが消えると、戻る/進むが壊れる。コラボレーションのキャッシュも残る | 履歴から該当 ID を除き、親へ移動する。コラボレーションのキャッシュを破棄する |
| 新規フォルダ | 影響は小さい | キャッシュ破棄のみ |

## 7. ファイルへのコラボレーションと、選択

### 7.1 要件

- 今は、**今開いているフォルダ**だけがコラボレーションの対象。
- 将来、**ファイルもコラボレーションの対象にしたい**ニーズが出る可能性がある。使うかどうかは未定のため、**入口側のコードをコメントアウトで保留**している（§7.5）。

### 7.2 Explorer の制約

- Explorer には、**外から選択状態を指定する手段がない**。行のハイライトを、こちらから制御することはできない（`navigateTo` と `clearCache` 系のみ）。
- 26.0.0 の `explorer.js` は、`select` 等のイベントを `emit` する。ただし、`select` の発火タイミングと引数は、ソースだけでは確定できていない（フォルダ行のクリックは、選択ではなく移動になる可能性が高い）。
- 画面側で対象を示すため、**独自パネルに「操作対象」を表示**する（ハイライトの代わり）。

### 7.3 採用案: `itemActions`（行の「…」メニュー）

26.0.0 の Explorer には、`itemActions` がある。各行の「…」メニューに、独自項目を足せる。

```ts
itemActions: [
  { label: "コラボレーション対象にする", type: "file", onAction: (item) => ... },
]
```

- 項目は `label` / `onAction(item)` / `type` / `filter`。`type` を省略するとフォルダにも出る。
- `canDelete` 等が全て `false` でも、独自項目が 1 件以上あれば、「…」メニューは出る。
- 動作:
  1. 操作対象の既定は、今開いているフォルダ。
  2. ファイル行の「…」から「コラボレーション対象にする」を選ぶと、そのファイルが対象になる（上書き）。
  3. フォルダを移動したら、ファイルの選択は解除し、既定（今のフォルダ）に戻る。
  4. パネルの見出しに、対象の名前と種別（ファイル/フォルダ）を表示する。
- **未確認**: `show()` の options から `itemActions` が渡るか（props にそのまま渡る作りだが、実機確認が要る）。「…」がホバー時のみ出る可能性。

他の案との比較:

| 案 | 評価 |
|---|---|
| `select` イベントを拾う（行クリック） | 発火条件が未確認。フォルダ行は移動になる。`canPreview` との兼ね合いも未確認 |
| `itemActions`（採用案） | 意図が明確。標準の挙動と衝突しにくい。フォルダにも付けられる。操作が 1 つ増える |
| 自前の一覧に置き換える | 見た目も選択も自由だが、Explorer の機能を作り直すことになる |

### 7.4 コラボレーション側の変更点（有効にするとき）

| 項目 | 内容 |
|---|---|
| 対象の型 | 今はフォルダ ID のみ。`{ type: "file" \| "folder", id }` に広げる |
| Box API | コラボレーションの作成は `item.type` に `file` を指定できる。一覧は、フォルダが `/folders/{id}/collaborations`、ファイルが `/files/{id}/collaborations` |
| キャッシュ | `ssSlice` の一覧は、フォルダ ID がキー。Box の ID は、フォルダとファイルで重複しうるため、キーに type を含める |
| 継承 | ファイルのコラボレーションにも、親フォルダからの継承分が含まれる。既存の継承表示（`sourcePathByFolderId`）の、ファイル版が要る |
| ロール | ファイルで使えるロールは、フォルダと一部異なる。既存のロール選択肢の見直しが要る |
| UI | 対象がファイルのとき、パスバーとフォームの見出し・文言を出し分ける |
| トークン | 対象のファイルはルートの配下。`resource` をルートにしていれば足りる |

## 8. 実装の順序（案）

1. CDN を 26.0.0 に上げ、既存機能が動くか確認する（§6）。
2. モックの `getContentsPickerToken` を、ルートと機能を受け取る形に拡張する。
3. スライスのトークン保持をルート単位にし、期限前の再発行を入れる。
4. `show()` の `can*` を、トークンの機能と連動させる。
5. 変更系イベントでのキャッシュ破棄と、パス・履歴の補正（§5）。
6. ファイルのコラボレーション（§7）。使う場合のみ。`itemActions` を実機で確認し、[FILE-COLLAB] のコメントアウトを外して、§7.4 を実装する。
