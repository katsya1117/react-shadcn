# 設計: 権限に影響する更新のあとの、ログインユーザー情報の取り直し

状態: 参照実装を、このリポジトリに入れた（実アプリへの反映は、別途）

関連: [redux-post-delete-refetch.md](./redux-post-delete-refetch.md)（更新直後の再 fetch が、本番で古い値を返すことがある件）

## 1. 課題
SS 画面からユーザー管理・センター管理へ移り、ユーザーが**自身の権限を編集**してから SS 画面へ戻ると、SS 画面が見ているログインユーザーの権限が、**更新前のまま**になり、操作を続けられてしまう。

原因は、ログインユーザーの情報（`user.loginUserInfo`）を、取得したあと、取り直す処理がないこと。

- 更新の保存（`updateUserInfo.fulfilled` など）は、`loginUserInfo` に触れない。
- 実アプリには、ログインユーザーが空のときだけ取得する処理（Layout 系）があると想定しているが、**一度取得したあとは取り直さない**。

## 2. 方針
**権限に影響しうる更新が成功したら、その場で、ログインユーザーの情報を取り直す。**

- 更新の時点で取り直すので、**そのあとにどのメニューへ移っても**、反映されている。新しいメニューを増やしても、画面ごとの対応は要らない。
- 画面（SS など）には、何も足さない。Layout 系も触らない。

### 採用しなかった案
| 案 | 内容 | 採用しない理由 |
|---|---|---|
| SS 画面のマウント時に取り直す | SS 画面に入るたびに取得する | 画面ごとの対応になる。メニューが増えるたびに、同じ対応が要る |
| 「古い」の印 + 上位で自動取得 | 更新の成功で印を立て、Layout 系の「空なら取得」に「または印がある」を足す | 仕組み（印、束ねる一覧、Layout の変更）が増える。更新の中で取り直す案のほうが、読みやすい |

## 3. 実装

### 3.1 取り直しの処理（`refreshLoginUser`、`userSlice.ts`）
`getLoginUserInfo` とは別の処理にしている。違いは次のとおり。

| | `getLoginUserInfo` | `refreshLoginUser` |
|---|---|---|
| 用途 | 初回の取得 | 更新後の取り直し |
| `isLoading` | 立てる | **立てない**（`isLoading` はユーザー一覧の読み込みと共有で、取り直しの間に一覧が読み込み表示になるのを避ける） |
| 失敗したとき | エラーを state に入れる | **エラーを出さず、今の情報を残す**（呼び出し元の保存の成否に影響させない） |
| ログインユーザーが空 | | 何もしない |

成功時の反映（`loginUserInfo` の更新と、API ヘッダの更新）は、`applyLoginUserInfo` に共通化している。

### 3.2 呼び出す場所
次の 6 つの更新が**成功したとき**に、`void dispatch(refreshLoginUser())` を呼ぶ（待たない。失敗したときは呼ばない）。

| スライス | 更新 |
|---|---|
| `userSlice` | `updateUserInfo`、`userCreation`、`removeUser` |
| `centerSlice` | `createCenter`、`updateCenterInfo`、`removeCenter` |

権限に影響する更新を足すときは、その成功のところに同じ 1 行を足す。

### 3.3 テスト
`src/redux/slices/refreshLoginUser.test.ts`: ログインユーザーが空なら何もしない、反映する、`isLoading` を立てない、失敗しても情報が残る、6 つの更新それぞれで「成功なら取り直す、失敗なら取り直さない」。

## 4. 注意点
- **取り直しの値が、古いことがある。** 更新の直後の再取得は、本番で、書き込みの反映の遅れ（DB のレプリケーション遅延、キャッシュ）により、古い値を返すことがある（[redux-post-delete-refetch.md](./redux-post-delete-refetch.md)）。権限が一向に変わらない場合は、まずここを疑う。対策は、GET の `Cache-Control: no-cache`、取り直しの少し後ろ倒し、など。
- **他の管理者が、ログインユーザーの権限を変えた場合は、検知できない。** この方式は、ログインユーザー自身の操作のあとだけが対象。これは、**サーバー側の検証（権限がなければ 403）**で守る部分。画面の権限表示は、あくまで表示の都合。403 を受けたときに取り直す処理は、次の段階の候補。
- **権限を読む画面は、ストアの値を直接読むこと。** マウント時に `useState` や `useRef` にコピーすると、ストアが更新されても、画面の値は古いままになる。
- **`centerSlice` が `userSlice` を読み込む。** 逆向き（`userSlice` が `centerSlice` を読み込む）にすると、循環参照になる。

## 5. 実アプリへの反映
コードを共有できないため、この設計書の内容を元に、実アプリ側で行う。

1. 取り直しの処理（3.1）を作る。取得は、実アプリの `getLoginUserInfo` と同じ API を使う。
2. 成功時の反映を、`getLoginUserInfo` と共通化する（実アプリがほかの処理を持っていれば、それも揃える）。
3. 権限に影響する更新（3.2）の成功のところに、1 行足す。実アプリで、対象をすべて洗い出す（権限テンプレート、ユーザーとセンターの紐付け、ロールの管理など、このリポジトリにないものを含む）。
4. userSlice を `jest.mock` で差し替えているテストのモックに、取り直しの処理を足す。
5. テストを書く（3.3）。
6. SS 画面が権限をストアから直接読んでいるかを確認する（4 章）。
