# Tips: コンポーネントの切り出しと、props / hook の置き場所、再描画の最適化

汎用のメモ。コンポーネントが長くなって切り出すとき、「何を props で渡し、何を子で直接呼ぶか」で迷ったら、これを見る。

## 1. 先に結論（迷ったとき）

1. まず、**子で呼ぶ形**で切り出す（hook、selector、dispatch、import した関数）。
2. 親も使うと分かったら、**親へ持ち上げて**、props で渡す。
3. 遅いと感じたら、**計測してから**最適化する（`memo` などを最初から散らさない）。

持ち上げるのは簡単だが、要らない props を減らすのは、呼び出し側の修正が増える。だから、1 → 2 の順が安全。

## 2. props で渡すか、子で呼ぶか

| 状況 | 置き場所 |
|---|---|
| **子だけ**が使う（子の中の `useState`、子でしか読まない selector、`useEffect`、import した関数） | **子で直接呼ぶ**。切り出すとき、一緒に子へ移す |
| **親も**使う、または**兄弟の子**も使う | **親が持って、props で渡す**（state の持ち上げ） |
| 子が**別の場所で、別のデータで**再利用される | props で受ける（中身を知らない部品にする） |

### 見分けの質問（上から順に）
1. この値や処理を、**親の他の場所でも使うか**。使うなら親が持つ（props）。
2. 使わないなら、**子が自分で呼べるか**（Redux や import で取れるか）。取れるなら子で呼ぶ。
3. props が **5〜7 個を超える**、または**途中の部品を素通りさせている**（孫まで届けるだけ）なら、子が直接 Redux から読む形を検討する。

### 何を props で渡すか
- **親が持っている state や、親が決める値**（開閉、選択中のもの、絞り込みの文字列など）
- **イベントの通知**（`onChange`、`onBack` など）。子が「起きたこと」を伝え、親が state を更新する
- 表示に必要な値で、親がすでに持っているもの

### 子で呼んでよいもの
- hook、selector、dispatch（子だけが使うなら）
- import した関数やユーティリティ（整形、パス組み立てなど）。props では渡さない

### よくある間違い
- 親で読んだ selector の結果を、子に渡すだけ（子だけが使う）。→ 子で読む
- `value` と `setValue` を、何段も素通りさせる。→ 使う場所に近い部品に state を持たせるか、Redux に置く
- 子が親に依存しすぎて、単体でテストできない。→ props を受ける形にする（Redux を読む子は、テストにストアが要る）

## 3. 長い理由で、切り出し方が違う

| 長い理由 | 切り出し方 |
|---|---|
| **JSX が長い** | 部品（コンポーネント）に切り出す。2 章の基準で、子で呼ぶものと、props で渡すものを分ける |
| **ロジック（state、effect、handler）が長い** | 部品ではなく、**自作 hook**（`useXxx`）に切り出す。見た目は変わらず、親が薄くなる |

## 4. レンダリング回数の観点

### 再描画される条件
1. 自分の **state が変わった**
2. **親が再描画された**（`React.memo` で包んでいなければ、props が同じでも、子はすべて再描画される）
3. 読んでいる **Context が変わった**
4. `useSelector` で読んでいる**値が変わった**（参照が違えば、変わったとみなす）

→ **state や selector を置いた場所が、再描画が広がる範囲を決める。**

### 判断が変わる点

**① state は、使う場所に一番近い所に置く**
- 頻繁に変わる値（入力中の文字、ホバー、スクロール位置）は、できるだけ小さい部品の中に閉じ込める。親に置くと、1 文字ごとに、親と配下のすべてが再描画される。
- ほとんど変わらない値（ログイン情報、設定など）は、持ち上げても害が小さい。

**② `useSelector` は、使う子で、小さく読む**
- 親で読むと、値が変わるたびに、親と配下が再描画される。使う子で読めば、その子だけ。
- スライス全体やオブジェクト全体ではなく、必要な項目だけを読む。
- selector の中で `.filter()` / `.map()` をして、毎回**新しい配列を返す**と、ストアが何か更新されるたびに再描画される。`createSelector` で包む（元の値が同じなら前回の結果を返す）か、素の値を読んで `useMemo` で加工する。

**③ props で渡す関数は、`memo` と相性が悪い**
- `React.memo` は、props が前回と**同じ参照**のときだけ、子の再描画を省く。親の中で書いた関数やオブジェクトは、再描画のたびに新しい参照になるので、`memo` が効かない。
- `memo` を使うなら、関数は `useCallback`、オブジェクトは `useMemo` で安定させる。
- 子がストアを直接読む形なら、親の関数に依存しないので、この問題は起きない。

### 使える技
| 技 | 内容 |
|---|---|
| state を下へ移す（コロケーション） | 入力欄など、頻繁に変わる state を、その部品の中に閉じ込める |
| `children` で受ける | 状態を持つ部品が `{children}` を受けると、`children` は親が作った同じ要素なので、状態が変わっても中身は再描画されない |
| `React.memo` | 重い子に使う。props を安定させることが前提 |
| 必要な範囲だけ読む | `useSelector` で読む値を絞る |

### 進め方
1. まず「使う場所に近い」構造にする。
2. 遅いと感じたら、React DevTools の **Profiler** で、実際に重い再描画を見つける。
3. 必要な所にだけ `memo` などを足す。

最初から `memo` や `useCallback` を散らすと、読みにくくなるわりに、効果がない場合が多い。React Compiler（自動で `memo` 相当を行う仕組み）を有効にすれば、手書きの多くは不要になる。このプロジェクトでは、有効にしていない（`package.json` / `vite.config.ts` に設定がない）。

## 5. このリポジトリの例

- **`PathBar` / `CollaborationPanel`（SS 画面）**: props だけの部品。親（SS 画面）が `useBoxExplorer` で履歴を持っていて、戻る・進むの状態を props で渡す。親が持つ state を表示するだけなので、props が自然。
- **ランチャー（`ShareArea`）の絞り込み**: 絞り込み欄（パネルの見出し側）と一覧（中）の両方が使うので、絞り込みの文字列（`query`）は、親（`ShareArea`）が持つ。持ち上げが必要な例。
  - その結果、1 文字入力するたびに、ページ全体が再描画され、`My Center` のカードも再描画される。今の件数（20 枚程度）では問題にならない。重くなったら、`My Center` の部分を、`query` に関係しない別の部品に切り出して `React.memo` で包む。
- **hook への切り出し**: `useBoxExplorer`（フォルダ移動の状態管理）。見た目ではなくロジックが長いときの例。

## 6. チェックリスト（切り出す前に）
- [ ] この値や処理は、子だけが使うか。（使うなら子で呼ぶ）
- [ ] 親の別の場所でも使うか。（使うなら親が持って、props）
- [ ] props が増えすぎていないか。素通りしていないか。（子で直接読む形を検討）
- [ ] 頻繁に変わる値を、親に置いていないか。（小さい部品に閉じ込める）
- [ ] `useSelector` の結果が、毎回新しい配列・オブジェクトになっていないか。
- [ ] 最適化は、計測してからにしたか。
