# 設計: 共有領域のランチャー（他センターから共有されたフォルダの表示）

状態: 検討中（方針は決定済み。実装前）

関連: [memo-sharearea-box-visibility.md](./memo-sharearea-box-visibility.md)（検討の経緯と、採用しなかった案）、[screen-spec-user-sharearea-ss.md](./screen-spec-user-sharearea-ss.md)（現在の画面仕様）

## 1. 目的と方針

### 1.1 課題
現在の ShareArea は、ユーザーが **所属（メンバー）またはゲストのセンター** だけをカードに出す。
他センターから、**センターの下層フォルダにだけ共有（コラボレート）された領域** は出ない。
ランチャー（目的の領域へ移動するための画面）の役割が満たされていない。

### 1.2 方針
1. 画面を 2 つに分ける。
   - **ランチャー**: 全員が使う。所属・ゲスト・共有を、種別が見分けられるように出す。
   - **管理画面**: 従来の ShareArea を、管理者専用に切り出す。コラボレーション設定とメンバー一覧を持つ。
2. 共有された領域は、**共有されたフォルダごとに 1 枚のカード** にする。カードから、その領域へ直接移動する（センターのトップから降りていかない）。
3. 共有の情報は、**アプリの DB に記録する**。ランチャーの一覧表示と、Box Drive ボタンの押下では、**Box を呼ばない**。
4. フォルダ名・経路の変更への追従は、**夜間バッチ** で行う（最大 1 日遅れ）。

### 1.3 採用しなかった案（概要）
| 案 | 内容 | 採用しない理由 |
|---|---|---|
| ユーザーごとの件数管理 | 利用者ごとに共有の件数を持つ | 管理が複雑 |
| ユーザーとして Box を探索 | `withUserSubject` で、センター配下をたどる | 一覧を開くたびに API を消費する。深いフォルダはたどる回数が増える |
| 表示のたびに名前を取得 | `folders/{id}` で最新の名前を取る | 名前の追従のためだけに API を消費するのは割に合わない |

## 2. 画面

### 2.1 ランチャー
区分けは 2 つ。見出しは「アイコン + 英字の小見出し + タイトル + 件数 + 右へ消える罫線」で、色で分ける。どちらもカードで、共有は 2 段組。

```
MY CENTER（primary）  所属センター [4]
  [センターA] [センターB] [センターC]            ← カード（3 列）

MY COLLABORATION（sky） 共有された領域 [7]   [🔍 絞り込み]
  ┌──────────────────────────────┐ ┌──────────────────────────────┐
  │ (🏢 センターD)     [Box][Drive] │ │ (🏢 センターD)     [Box][Drive] │
  │ 📁 見積資料  共有 編集者         │ │ 📁 契約書  共有 閲覧者           │
  │ センターD › 2024年度 › … › 見積資料 │ │ センターD › 2024年度 › 法務 › 契約書 │
  └──────────────────────────────┘ └──────────────────────────────┘
                   [ すべて表示（あと 2 件） ]
```

- 共有が 5 件を超えるときだけ、最初は 5 件に絞って「すべて表示」を出し、絞り込み（センター名・フォルダ名・パス）の入力欄も出す。絞り込み中は、一致するものをすべて出す。

### 2.2 共有のカード
| 位置 | 内容 | 元の項目 |
|---|---|---|
| 上段 | センターの表示名（「〇〇センター」）のラベル（建物アイコンつきの丸いラベル）と、Web Box / Box Drive のボタン | センターの表示名、フォルダ ID、経路 |
| 中段 | フォルダ名、「共有」とロールのバッジ | フォルダ名、ロール |
| 下段 | フルパス（`センター名 › 経路 › フォルダ名`）。2 行まで折り返す | センターのフォルダ名、経路、フォルダ名 |
| 状態 | 「見つからない」のときは、グレー表示にして、メッセージを出し、ボタンを無効にする | 状態 |

- コラボレーション設定のボタンは出さない（管理画面の機能）。
- **フルパスは組み立てて出す**: DB の項目は増やさない。`センターのフォルダ名 + path_names + folder_name` をつなげる。先頭は、ラベルの表示名ではなく、**Box 上のフォルダ名（英字）**。Box Drive のパスにそのまま使うため。
- 表示名（管理者が付ける呼び名）は設けない。フォルダ名は常に、夜間バッチが更新する Box 上のフォルダ名。
- **センター直下のとき**: フルパスはラベルとフォルダ名と同じ内容になるので、フルパスの行を出さない。
- **省略**: 長いときは、先頭の 1 つ（センター名）と末尾の 2 つを残して、間を `…` にする。`センターD › … › 案件A › 見積資料`。全文は、マウスを載せたときに出す（`title`）。
- 並び順: センター名、次に領域名。

### 2.3 ボタンの動き
| ボタン | 動き | Box への問い合わせ |
|---|---|---|
| Web Box | `https://app.box.com/folder/{フォルダ ID}` を開く | なし（ID なので、改名の影響を受けない） |
| Box Drive | DB の経路から、ローカルパスを組み立てて開く | なし |
| 起動 | センター単位の現状の挙動 | 要確認（共有されたフォルダでの扱いは未決） |

## 3. DB の構成

2 つのテーブルに分ける。バッチが一周するのは、重複のない「共有されたフォルダ」。

### 3.1 共有されたフォルダ（`shared_folder`、フォルダ ID で重複なし）
| 項目 | 内容 | 更新するもの |
|---|---|---|
| `folder_id`（主キー） | 共有されたフォルダの Box ID | 作成時のみ |
| `center_folder_id` | 属するセンターのフォルダ ID（SS 画面の `rootFolderId`） | 作成時のみ |
| `folder_name` | フォルダ名 | 作成時の値が初期値。以後は夜間バッチ |
| `path_names` | センターより下の名前の並び（共有されたフォルダ自身を除く） | 作成時の値が初期値。以後は夜間バッチ |
| `status` | `ok` / `missing` | 夜間バッチ |
| `synced_at` | 最後にバッチで同期した時刻 | 夜間バッチ |

### 3.2 共有の付与（`share_grant`、コラボレーションごと）
| 項目 | 内容 |
|---|---|
| `collaboration_id`（主キー） | Box のコラボレーション ID |
| `folder_id` | `shared_folder` への参照 |
| `principal_type` | `user` / `group` |
| `principal_id` | ユーザーまたはグループの ID |
| `role` | Box のロール（editor, viewer など） |

### 3.3 センターの名前の取得（`centerName` / `centerLabel`）
センターの名前は `shared_folder` にコピーせず、**センターのマスタから、一覧を作るときに引く**。

| 応答の項目 | 元 | 例 |
|---|---|---|
| `centerName`（Box 上のフォルダ名。英字。フルパス・Box Drive のパス用） | センターのマスタの `folder_name` | `JCLGD2SWDV` |
| `centerLabel`（表示名。カードのラベル用） | センターのマスタの `center_name` | 第2ソフトウェア開発センター |

- 既存の `CenterInfo`（`center_cd` / `center_name` / `folder_name`）が、そのまま使える。
- コピーしない理由: センター名が変わったときに、`shared_folder` の更新が要らない。夜間バッチの対象にもしない。
- **未決**: `shared_folder.center_folder_id`（Box のフォルダ ID）から、マスタの行を引く方法。このアプリでは、固定の設定（`SHARE_AREAS`）が対応を持っているが、`CenterInfo` には Box のフォルダ ID の項目がない。本番の DB に対応があるかを確認する。無ければ、`shared_folder` に `center_cd` を持たせる（追加時に、SS 画面のセンターから分かる）。

### 3.4 グループの所属
グループが対象の共有を判定するため、「ユーザー → グループ」の対応が DB に必要。
既存の仕組みにあるものを使う。無ければ、別途用意する（要確認）。

## 4. 書き込み（共有の追加・変更・削除）

共有の操作は SS 画面（管理画面）から行う。Box の操作に成功したあとで、DB を更新する。

| 操作 | Box | DB |
|---|---|---|
| 追加 | コラボレーションを作成 | `shared_folder` に無ければ作成（`folder_id`、`center_folder_id`、`folder_name`、`path_names` を、そのときの値で）。`share_grant` を追加 |
| ロール変更 | コラボレーションを更新 | `share_grant.role` を更新 |
| 削除 | コラボレーションを削除 | `share_grant` を削除。そのフォルダの付与が 0 件になったら、`shared_folder` の行も削除 |

### 4.1 追加時に使う値
SS 画面の `currentFolder`（`useBoxExplorer` が持つ現在地）から取る。

- `folder_id` = `currentFolder.id`
- `folder_name` = `currentFolder.name`
- `path_names` = `currentFolder.pathCollection.entries` のうち、**センターのフォルダより後ろ**の名前（現在地自身は含めない）
- `center_folder_id` = `rootFolderId`

### 4.2 対象外とするもの
センターのフォルダそのものへの共有（`folder_id` = `center_folder_id`）は、従来どおり所属・ゲストの扱い。`shared_folder` には入れない。

## 5. 一覧表示のロジック

ランチャーを開いたとき、サーバーが DB だけで組み立てる。

### 5.1 手順
1. ログインユーザーの所属・ゲストのセンターを取得する（既存の処理）。
2. 対象が **自分**、または **自分が属するグループ** の `share_grant` を取得する。
3. 対象のセンターが、手順 1 のセンターに含まれるものを除く（所属と共有の二重表示を防ぐ）。
4. `folder_id` ごとにまとめる。同じフォルダに複数の付与があるときは、**最も強いロール** を採用する（Box でも強い権限が有効になる）。
5. `shared_folder` を結合して、カード用の項目を作る。
6. センターのフォルダ名を付けて、センター名、領域名の順に並べる。

### 5.2 SQL の目安
```sql
SELECT sf.folder_id, sf.center_folder_id, sf.folder_name, sf.path_names,
       sf.status,
       MAX_BY_ROLE(g.role) AS role         -- ロールの強さで選ぶ（実装時に決める）
FROM share_grant g
JOIN shared_folder sf ON sf.folder_id = g.folder_id
WHERE ((g.principal_type = 'user'  AND g.principal_id = :userId)
    OR (g.principal_type = 'group' AND g.principal_id IN (:userGroupIds)))
  AND sf.center_folder_id NOT IN (:belongingCenterFolderIds)
GROUP BY sf.folder_id;
```

### 5.3 API の応答（案）
既存の一覧に、`shared` を追加する。

```ts
type SharedAreaItem = {
  folderId: string;
  centerFolderId: string;
  centerName: string;      // センターのフォルダ名（英字）。フルパス・Box Drive のパス用
  centerLabel: string;     // センターの表示名（〇〇センター）。カードのラベル用
  pathNames: string[];     // センターより下の経路（フルパスは centerName + pathNames + folder_name で組み立てる）
  folderName: string;      // Box 上のフォルダ名（タイトルと、フルパスの末尾に使う）
  role: string;
  status: "ok" | "missing";
};
```

| 場所 | 内容 |
|---|---|
| ランチャー画面 | 新設。所属・ゲスト・共有を出す |
| 管理画面 | 従来の ShareArea（SS）を、管理者専用にする |
| Redux | ランチャーの一覧は、`ss` スライスとは別。1 回取得して、画面を開くたびに取り直す |
| モック（`src/api/mock/`） | `shared_folder`、`share_grant`、グループ所属のデータを追加 |

## 6. 夜間バッチ

`shared_folder` を一周する。1 行につき 1 回、Box を呼ぶ。

```
GET /folders/{folder_id}?fields=name,path_collection
```

| 結果 | 更新 |
|---|---|
| 成功 | `folder_name`、`path_names`（センターより下の名前の並び）を更新。`status = ok`。`synced_at` を更新 |
| 404 / 権限エラー | `status = missing`（削除または権限喪失） |

- 1 回の取得で、名前と経路の両方と、削除・権限喪失の検知ができる。階層の深さで消費は増えない。
- 途中のフォルダが改名されたときは、その下の共有されたフォルダが、それぞれ次の夜に更新される。

### 6.1 API の消費（毎晩実行、30 日、上限 100,000 / 月に対して）
| 共有されたフォルダの数 | 月間 | 割合 |
|---|---|---|
| 200 | 6,000 | 6% |
| 500 | 15,000 | 15% |
| 1,000 | 30,000 | 30% |

（仮定の数値。実際の件数で見積り直す。）多いときは、週 1 回にする、対象を絞る、などで抑える。

### 6.2 Box の呼び出しの権限（未決）
サービスアカウントは、共有されたフォルダにアクセスできないことがある。候補:

- 共有の対象のユーザー自身として呼ぶ（`withUserSubject`）。グループが対象のときは、そのメンバーの 1 人として。
- 管理者として呼ぶ（管理者がすべてのフォルダを見られる場合）。

`path_collection` に途中の名前が出るかは、呼ぶ権限による。`can_view_path` があれば見える。

## 7. 必要な API

ランチャーの一覧のために**新しく作る API は 1 つ**。残りは、既存のコラボレーション API に DB の更新を足す変更と、バッチ。

### 7.1 一覧（新規）
| 項目 | 内容 |
|---|---|
| 用途 | ランチャーの「共有された領域」の一覧 |
| 呼ぶ場所 | ランチャーを開いたとき（`getSharedAreas`） |
| 入力 | ログインユーザー（認証情報から。モックでは `userCd` を渡している） |
| 出力 | `SharedAreaItem[]`（5.3）。センター名、フォルダ名の順に並べ済み |
| 処理 | 5.1 の手順。DB のみ。**Box は呼ばない** |
| 依存 | 所属・ゲストのセンター（既存の所属の一覧と同じ取得）、グループの所属（3.4）、センターのマスタ（3.3） |

所属・ゲストのカードの一覧は、既存の API（DB の所属に応じて返す）のまま。

### 7.2 コラボレーションの追加・変更・削除（既存 API の変更）
画面（SS）が使う、コラボレーションの API（`BoxApi.createCollaborations` / `updateCollaboration` / `deleteCollaborations`）で、**Box の操作が成功したあとに、DB を更新する**。Box の呼び出し自体は変えない。

| API | 入力に足すもの | DB の更新 |
|---|---|---|
| 追加 `createCollaborations` | `centerFolderId`（SS 画面の `rootFolderId`）、`folderName`、`pathNames`（4.1） | `shared_folder` に無ければ作成。`share_grant` を追加。`principal_type` は、Box の `accessible_by.type`（`user` / `group`）に合わせる |
| 変更 `updateCollaboration` | なし（`collaborationId` で足りる） | `share_grant.role` を更新 |
| 削除 `deleteCollaborations` | なし（`collaborationId` で足りる） | `share_grant` を削除。そのフォルダの付与が 0 件なら `shared_folder` も削除 |

- 追加の入力は、画面が持っている現在地（`currentFolder`）の値を送る。サーバーが Box から取り直すと、追加のたびに Box を 1 回余分に呼ぶことになる。
- センター直下への共有（`folderId` = `centerFolderId`）は、DB に記録しない（4.2）。
- `canViewPath` は、DB に持たない（一覧に使わない）。

### 7.3 夜間バッチ（HTTP の API ではない）
6 章のとおり。`shared_folder` を一周して、Box の `GET /folders/{id}?fields=name,path_collection` を呼び、名前・経路・状態を更新する。実行の仕組み（cron など）と、Box を呼ぶ権限は未決（6.2）。

### 7.4 作らないもの
- ユーザーが見られるフォルダを、Box から列挙する API
- 表示名を設定する API（表示名は設けない）
- Box Drive のボタンのための API（DB の経路から組み立てる。2.3）

| 7.2 追加・変更・削除の DB 更新 | 未実装（モックの `ssCollaborationsDb` は、`shared_folder` / `share_grant` を更新しない） |

## 8. 弱点と、許容する点

| 項目 | 内容 | 扱い |
|---|---|---|
| 名前・経路の遅れ | 最大 1 日。改名の直後は、Box Drive のパスが正しく開けないことがある | 許容 |
| 既存の共有 | この機能の前に作られた共有は、DB に無いので出ない | 取り込み処理（Box のコラボレーションを走査して DB に入れる）が別途必要。当面は考えない |
| アプリを通さない共有 | Box 側で直接つけた共有は出ない | 許容 |
| Box と DB の不整合 | Box の操作は成功し、DB の更新が失敗する場合 | 許容（必要になれば再試行や整合チェックを検討） |
| 削除されたフォルダ | バッチで `missing` になるまで、カードが残る | 許容 |
